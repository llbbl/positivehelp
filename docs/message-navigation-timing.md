# Investigating message navigation latency

The message page currently fetches the website's own `/api/messages/[slug]`
endpoint. That handler performs three sequential database reads. Timing these
boundaries helps distinguish slow database calls from time spent outside the
handler before changing the queries, caching, or database client.

## What is measured

Every response returned by the detail handler includes:

- `X-Message-Request-Id`: a fresh UUID generated by the handler. Incoming IDs are
  ignored. The same ID appears in the `message_api_timing` server log.
- `Server-Timing`: elapsed milliseconds for completed or failed operations.
  `rate_limit` covers the rate limiter; `lookup`, `navigation`, and `message`
  cover the three awaited database calls. `total` covers handler work up to
  response decoration, including JSON serialization. Absent phases were not run.

These are elapsed operation times, **not database engine execution times**.
Database metrics also include client, connection, network, and result handling
costs. `total` overlaps the phase durations; do not add it to their sum.
The handler timer starts after middleware and excludes final timing-log emission,
response transfer, and browser work. It does not isolate Clerk or proxy latency.

The page emits `message_page_fetch_timing` once per actual execution of its
React-cached message reader. It contains:

- `requestId`, when the API returned a valid UUID, joining the page and API logs;
- HTTP `status` when headers were received, and `outcome` (`found`, `not-found`,
  or `error`);
- `timings.fetch` from starting `fetch` until response headers arrive (or it
  rejects), `timings.parse` for body transfer and JSON parsing when attempted,
  and `timings.total` for the reader.

A 404 remains missing content. Rate limits, other HTTP failures, network errors,
and malformed JSON remain errors. Failed operations retain their elapsed time.
The new timing records contain no message text, author, URL/query string, cookie,
IP address, authorization header, SQL, or database credentials. Existing error
logs are separate. Timing runs for every detail read; there is no sampling or
new environment variable. It adds one API completion log; the page's completion
log replaces its two previous success-path info logs.

The API's headers are on the **internal API response**, not automatically on
`/msg/[slug]` HTML or RSC responses. Use server logs for the page-to-API join.
These measurements are not keyboard-to-paint latency, full page render time,
or a measurement of React cache hits.

## Collecting comparable evidence

1. Confirm the deployed commit includes this instrumentation. Record commit,
   instance, time window, browser/version, authentication state, and test slugs.
2. In Chrome or Vivaldi DevTools, preserve the Network log and capture a
   Performance recording while navigating with B/N. Separate first visits from
   repeated visits. Record actual RSC requests, cache/prefetch hits, status,
   redirects, and visible message updates. A hand-built `RSC: 1` request that
   redirects is not a navigation sample.
3. For each slow period, collect paired `message_page_fetch_timing` and
   `message_api_timing` records by `requestId`. Use timestamps to locate the
   relevant page logs; overlapping browser requests cannot be matched exactly
   from these server IDs alone. Direct API probes can join by the response ID.
4. Compare enough repeated samples under the same conditions to describe the
   distribution, including median and slow-tail observations. Keep failed,
   rate-limited, and cache-served responses separate. Stay below the public
   rate limit; this is not a load-test procedure.
5. If awaited database operations dominate, evaluate consolidating reads. If
   page fetch time substantially exceeds API total, investigate the self-fetch
   path and middleware/proxy overhead. If server timings are small while the
   visible transition is slow, inspect browser/RSC rendering and navigation.
   None of those differences alone proves which component caused the delay.

A direct API sample (substitute a published slug):

```sh
curl --silent --show-error --dump-header - --output /dev/null \
  --write-out 'ttfb=%{time_starttransfer}s total=%{time_total}s\n' \
  'https://positive.help/api/messages/<slug>'
```

Never share unsanitized HAR files: browser recordings may contain credentials.
The initial six-per-endpoint investigation reproduced variable HTTP latency but
had no stage timings and no browser paint measurement. This instrumentation
establishes the next baseline; it does not claim a speed improvement.

Server-Timing syntax is documented in the
[MDN header reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing).
Query consolidation, removal of the HTTP self-fetch, bounded prefetch, and Turso
Sync remain evaluations tracked in [issue #325](https://github.com/llbbl/positivehelp/issues/325).
